# Migrating Existing `.mpm` Files

This guide helps operators who have an existing `.mpm` file -- written by hand
or generated by an earlier `mpm bootstrap` invocation (`mpm bootstrap` was
removed in mpm 3.0.0) -- adopt the `search`, `add`, and lockfile features.

## Audience

You are an operator who already has a `.mpm` file in your workspace. Your file
was created before the `mpm search`, `mpm add`, `mpm remove`, and lockfile
features existed. You want to know what changes with a fresh `mpm install`, and
how to bring the file fully into compliance with the current standard.

If you are starting from scratch, see [list-and-add.md](list-and-add.md) instead.

## First install: lockfile generation

When you run `mpm install` for the first time against an existing `.mpm` file
after upgrading to this release, mpm writes a new file alongside it:

```text
.mpm          <-- your existing file (unchanged)
.mpm.lock     <-- written by mpm install on first run
```

The lockfile captures the resolved git SHAs for every source and every transitive
project at install time. On every subsequent install, mpm reads these pinned SHAs
and installs exactly the same code -- regardless of what new tags or commits have
appeared upstream.

**You must commit both files.** Once `.mpm.lock` exists, your repository has a
reproducible install record. Team members and CI pipelines running `mpm install`
from the same commit will receive byte-for-byte identical checkouts.

Concretely, after the first run:

```shell
# First install against an existing .mpm
mpm install
# mpm prints: "lockfile rebuilt from .mpm (N sources, M projects)"

git add .mpm .mpm.lock
git commit -m "add mpm lockfile"
```

From this point forward, `mpm install` prints:

```text
installing from lockfile (N sources, M projects)
```

To re-resolve all versions (e.g., after bumping a revision spec in `.mpm`),
run:

```shell
mpm install --refresh-lock
```

See [lockfile.md](lockfile.md) for the full lockfile format, conflict-resolution
rules, and refresh options.

## Source-name compliance

### The normalization rule

Every `MPM_SOURCE_<source-name>_*` block in your `.mpm` file uses a
**source name** (the alias) derived from the catalog entry name by this rule:

1. Lowercase the entire entry name.
2. Replace every `-` (hyphen) with `_` (underscore).

No other substitutions are made. The transformation is one-way and lossy.

Examples:

| Entry name (in catalog XML) | Derived source name (in `.mpm`) |
| --------------------------- | --------------------------------- |
| `my-package` | `my_package` |
| `Package-A` | `package_a` |
| `FooBar` | `foobar` |
| `internal_tool` | `internal_tool` (unchanged) |

`mpm add` always writes the normalized source name. If you added entries by hand
or via `mpm bootstrap`, the source names in your file may not match this rule.

### When it matters

A mismatch between the source name in your `.mpm` file and the name mpm would
derive from the catalog entry causes:

- `mpm remove <entry-name>` to report that the source is not found.
- `mpm install --refresh-lock-source <entry-name>` to fail with a lookup error.
- `mpm validate metadata` to emit a `source-name-derivation` warning for the
  affected entry.

### Warning on first install

On the first `mpm install` after upgrading, mpm scans the `MPM_SOURCE_*`
blocks in your `.mpm` file and emits a warning for each block whose key does
not match the normalized form of the corresponding catalog entry name:

```text
WARNING: source name 'Package-A' in .mpm does not match the normalized form
  'package_a' derived from catalog entry 'Package-A'.
  To bring the file into compliance, run:
    mpm remove 'Package-A' && mpm add 'Package-A@<your-spec>'
  Or hand-edit the MPM_SOURCE_Package-A_* keys to use the prefix
  MPM_SOURCE_package_a_*.
  See docs/migrating-existing-mpm-files.md#source-name-compliance.
```

Install continues after the warning. The warning is printed to stderr so it does
not break CI pipelines that capture stdout.

### Remediation path A -- use mpm remove and mpm add

This is the recommended path. It rebuilds the source block from the catalog and
guarantees the normalized source name:

```shell
# Replace Package-A with its normalized equivalent
mpm remove 'Package-A'
mpm add 'Package-A@<your-spec>'
```

After `mpm add`, the `.mpm` file contains `MPM_SOURCE_package_a_*` keys
with the correctly normalized alias. See [list-and-add.md](list-and-add.md) for
the full `mpm remove` and `mpm add` reference.

### Remediation path B -- hand-edit MPM_SOURCE_* keys

If you prefer to edit the file directly, rename the block keys in place:

Before:

```shell
MPM_SOURCE_Package-A_URL=https://example.invalid/org/catalog.git
MPM_SOURCE_Package-A_REF=main
MPM_SOURCE_Package-A_PATH=repo-specs/package-a-marketplace.xml
MPM_SOURCE_Package-A_NAME=Package-A
MPM_SOURCE_Package-A_GITBASE=https://example.invalid/org
```

After:

```shell
MPM_SOURCE_package_a_URL=https://example.invalid/org/catalog.git
MPM_SOURCE_package_a_REF=main
MPM_SOURCE_package_a_PATH=repo-specs/package-a-marketplace.xml
MPM_SOURCE_package_a_NAME=Package-A
MPM_SOURCE_package_a_GITBASE=https://example.invalid/org
```

Rename every key in the block in the same edit -- the required structural keys
(`_URL`, `_REF`, `_PATH`, `_NAME`) plus any optional per-dependency env-var line
(`_GITBASE` above, or any other `${VAR}` name your manifest uses) and the
optional `_MARKETPLACE`. Do not leave any of the old-named keys in the file.

## Common fixes

### No global header is required

There is **no required global header** in the current `.mpm` format. `mpm add`
writes self-contained alias-keyed blocks; when a source's manifest references
`${GITBASE}`, the org base is recorded per dependency in
`MPM_SOURCE_<alias>_GITBASE` (auto-derived from the source URL) rather than a
single global `GITBASE` line -- and a manifest that references no `${VAR}` gets
no env-var line at all. There is also no global `MPM_MARKETPLACE_INSTALL`
toggle: marketplace install is a per-dependency opt-in (see
[Marketplace install is per-dependency](#marketplace-install-is-per-dependency)
below).

The only global that is sometimes required is `CLAUDE_MARKETPLACES_DIR`, and only
when at least one dependency sets `MPM_SOURCE_<alias>_MARKETPLACE=true`:

```shell
CLAUDE_MARKETPLACES_DIR=/path/to/marketplaces
```

- `CLAUDE_MARKETPLACES_DIR` -- absolute path to the directory where marketplace
  plugins are installed. `mpm install` errors only when a marketplace
  dependency is declared but this variable is absent.

### Marketplace install is per-dependency

Earlier mpm used a single global `MPM_MARKETPLACE_INSTALL` toggle. That
variable was **removed**. Marketplace install is now an opt-in per dependency:
add `MPM_SOURCE_<alias>_MARKETPLACE=true` to that dependency's block (absence of
the line is the canonical false; mpm never writes `=false`). Manage the flag
with `mpm marketplace enable <alias>`, `mpm marketplace disable <alias>`, and
`mpm marketplace status`. If your hand-written file still has a global
`MPM_MARKETPLACE_INSTALL` line, delete it and set the per-dependency flag on
each marketplace source instead.

### Non-contiguous source blocks

Each source block consists of the alias-keyed lines:

```shell
MPM_SOURCE_<alias>_URL=...
MPM_SOURCE_<alias>_REF=...
MPM_SOURCE_<alias>_PATH=...
MPM_SOURCE_<alias>_NAME=...
MPM_SOURCE_<alias>_GITBASE=...
```

Hand-written files sometimes interleave comments or blank lines between the
keys of a single source block:

```shell
# Primary catalog
MPM_SOURCE_my_catalog_URL=https://example.invalid/org/catalog.git
# pinned to stable branch
MPM_SOURCE_my_catalog_REF=main
MPM_SOURCE_my_catalog_PATH=repo-specs/my-catalog-marketplace.xml
MPM_SOURCE_my_catalog_NAME=my-catalog
MPM_SOURCE_my_catalog_GITBASE=https://example.invalid/org
```

This is **allowed**. `mpm remove` locates every `MPM_SOURCE_<alias>_*`
line wherever it appears in the file and removes them, preserving the line order
of all remaining content. Non-contiguous blocks do not cause errors.

However, if you want to keep the file tidy for readability, group the three keys
for each source together without intervening lines.

### Stale REPO_URL and REPO_REV legacy env vars

Earlier versions of mpm used a single-source model with two global variables:

```shell
REPO_URL=https://example.invalid/org/old-catalog.git
REPO_REV=main
```

These variables are no longer read by `mpm install`. If `REPO_URL` or
`REPO_REV` are set as environment variables in your shell or CI environment,
mpm prints a warning on install:

```text
REPO_URL and REPO_REV environment variable(s) are deprecated and no longer used
by 'mpm install'. Use --catalog-source to specify a remote catalog source
instead.
```

To migrate:

1. Note the value of `REPO_URL` and `REPO_REV`.
2. Unset `REPO_URL` and/or `REPO_REV` from your shell environment and CI
   pipeline configuration.
3. Add a properly named source block using `mpm add`:

   ```shell
   mpm add '<entry-name>@<your-spec>'
   ```

   Or add the block by hand using the `MPM_SOURCE_<name>_*` format shown above.

See [troubleshooting.md](troubleshooting.md) for the full entry on this warning.

### Mixed line endings

If your `.mpm` file was edited with an editor that writes CRLF (`\r\n`)
line endings -- common when the file originated on a Windows host before
mpm ran under WSL2 -- it may contain a mixture of CRLF and LF (`\n`) line
endings. Windows itself is **not currently supported (planned)**; run mpm
under WSL2 (Windows Subsystem for Linux), where the `.mpm` file behaves
exactly as it does on Linux.

`mpm install` reads the file regardless of line-ending style. `mpm remove`
detects the dominant line ending in the file and preserves it. When the file
contains a mix, mpm normalizes all line endings to LF and prints a warning:

```text
WARNING: .mpm contains mixed line endings; normalized to LF.
```

If you want to fix this proactively, run the following inside WSL2, Linux,
or macOS:

```shell
sed -i 's/\r//' .mpm
```

After normalizing, verify the change with `git diff --check`.

### Missing trailing newline

POSIX requires text files to end with a newline. If your `.mpm` file lacks a
trailing newline, some tools emit warnings and git may display a `\ No newline at
end of file` diff marker.

`mpm install` reads files without a trailing newline without error. `mpm add`
always appends a trailing newline when it writes new source blocks. To fix an
existing file:

```shell
# Append a newline if missing (Linux/macOS)
[ -n "$(tail -c1 .mpm)" ] && echo >> .mpm
```

Verify with `cat -A .mpm | tail -1` -- the last line should end with `$`, not
`^M$`.
